# MAU-167 — synthetic screening and intake

This is a software-only slice of MAU-25 revision 3, authorized on November 22, 2026. It creates no research credit, authority grant, execution, qualification, external acquisition, or deployment. An intake marked `ready` permits draft promotion within this slice, not an approval. The four workflow ledgers remain independent.

## Browser journey and API

1. Sign in as an existing synthetic editor. From an Idea detail page, follow **Screening and prior research**. Create or revise a family and proposed case in **Research context**. The case form records the manual prior-search scope, fictional UTC query time, policy, result watermark, exact record edges, finding, reason, and limitations. Inspect its exact version. This is distinct from the operator's record search; no search was run or inferred by intake.
2. Enter the exact family and case version IDs. Assess every exact Source-to-Idea contribution and record all ten narrative priority dimensions. Classify an invented sibling as `related_variant` in the same family; `candidate` does not mean approved distinctness. If not viable, select **Record early closure**; this needs a family and reason/gate/evidence/limitations/lesson, not sufficient rights or a successful investigation.
3. Save, inspect exact screening history, and follow **Draft hypothesis with this exact intake**. The normal Hypothesis form receives the exact Idea, case, family association and intake IDs; the service revalidates them under the same transaction/advisory lock as upstream corrections. Use the existing Hypothesis → Test Plan workflow. For a correction, resubmit a full assessment against the current Idea, case, family, prior-search results, and rights, with the expected screening version and a correction reason. Earlier Source/Idea/case/assessment/Hypothesis/Plan pins are retained; a Plan linked to a stale screened Hypothesis cannot be progressed simply by changing a title.

The draft link and direct GET use the same read-only check over those exact inputs. A stale or mismatched link returns a generic `400` with a reassessment link, not a prefilled form. The transactional Hypothesis and Plan gates still recheck on write; browser readiness is not a write authorization. The legacy Idea draft shortcut remains available only for Ideas without screening history.

`GET /api/v1/ideas/{idea_id}/intake` returns authorized ordered screening versions, original and superseding IDs, exact endpoint IDs and downstream Hypothesis pins. Current grants are checked before returning each Source assessment's metadata and content. No source bytes are returned. Both routes prohibit caching. The authenticated browser POST uses CSRF.

`POST /api/v1/ideas/{idea_id}/intake` requires `Idempotency-Key` and a JSON object with `idea_version_id`, `family_version_id`, `outcome`, `distinctness`, `family_rationale` and `expected_latest_version` (zero for creation). Add `correction_reason` for a revision. A `ready` request adds `investigation_version_id`, `priority` (the named `PRIORITY` keys), and `source_assessments` (a map from exact contribution ID to `methodology_quality`, `claim_used`, `contrary_evidence`, and `limitations`). An `early_closed` request instead supplies `closure` (`reason`, `gate_reached`, `evidence_completeness`, `unresolved_mechanism`, and `reusable_lesson`). The write receipt contains only `stable_id`, `version_id`, and `version`; replay is historical and does not re-authorize progression. Stale screening writes and conflicting reuse return 409. Unknown and unscopeable IDs do not distinguish hidden records from missing ones.

`intake_version_id` is additive on Hypothesis creation, correction and read. The gate requires it if the Idea or case has screening history, or the predecessor was screened. No existing unbound legacy planning draft is upgraded to governed intake; those APIs still support unbound draft authoring to preserve existing synthetic flows. Future registration/dispatch integration must separately require screened lineage where mandated; this branch has no dispatch routes and is not an approval of the MAU-159 branch. Existing result and evidence behavior is untouched.

## Fixture-only rights and scope

`RMS_INTAKE_SYNTHETIC_RIGHTS` is an optional Django settings mapping; absent, malformed, expired, unmatched, revoked or changed grants fail closed. Each fixture grant is keyed by exact Source version ID and has `operation: synthetic_intake_assessment`, `sha256` of that version's stored bytes, a `reference` prefixed `fixture:`, and an aware RFC 3339 `expires_at`. Exact grant reference/expiry is retained in the assessment; the immutable contribution relates the Source bytes and digest. It is not a new rights service, and `rights_note` and user form fields cannot grant rights. An existing synthetic RMS editor can write; a founder viewer can read authorized history but cannot write here even with both groups. No real rights decisions or protected material are admitted. Tests use only generated in-memory fixture grants. Production rights records, operator authorization/configuration and custody are separate prerequisites for any later real-use design.

Ready intake versions also record the grant reference and UTC expiry for every exact Source linked through the manual prior-research assessment, including Sources that are not Idea contributions. That immutable assessment retains the Source edges and the referenced Source versions retain their digests. Progression compares the full stored mapping to validated current grants. A grant replacement, revocation, expiry or Source correction requires an appended reassessment; prior versions keep their original pins. The grant mapping is internal and is not rendered or returned by history endpoints.

## Schema, rollback and recovery

- On master base `25e8f4edcede91470881e2802c2927831b609606`, the atomic additive migrations are `0008_research_intake` after `0007` and `0009_intake_prior_rights` after `0008`. `0009` adds a nullable immutable column, with no new table, sequence or privilege requirement. New ready rows store a proved map (`{}` when there are no prior Source links); ready rows from before `0009` retain `NULL`, remain readable within their authorized scope, and require reassessment to progress. Do not backfill a missing proof from current rights. When combining with MAU-159 or sibling migration leaves, the Director must reconcile the graph and rerun fresh migration, upgrade and restore. No migration was applied to an installed or reserved database.
- The identity watermark advances only with an append, guarded by the existing PostgreSQL trigger. The new tables reject direct mutation and truncation. Deferred guards verify exact family/Idea/case/Hypothesis edges and seal the source-assessment set, including absence for an early closure. The lowest proposed app rights add `SELECT, INSERT` on the four new tables, plus column-scoped `UPDATE` of the identity key and watermark for row locking and append; there are no new sequences. Operations must verify ordinary-role grants and adopt the exact migration-leaf allowlist separately. No privilege provisioning is included.
- Roll application code back with the additive schema and guards retained; `0008` is intentionally irreversible, and reversing `0009` would discard grant evidence. Keep governed writes disabled when rolling back to code that does not enforce the revised gate. A failed forward migration rolls back with its SQL transaction. Do not remove tables, bypass guards, or reopen progression on a stale restored instance.
- Backup/restore must include the four tables (including the `prior_source_rights` column), constraints and triggers in the same consistent PostgreSQL snapshot as Source, Idea, family, case, Hypothesis, Plan and idempotency lineage. Independently reconcile identity watermarks, version/digest/edge counts, exact grant bindings, original and corrected records, and access denials before use. On a pre-`0009` restore, migrate before enabling the application; preserve missing grant proofs and require reassessment. Load current separately authorized fixture grants, not expired snapshot permissions. No external evidence objects were added. A local dump is not independent custody. True independent custody/DR remains a prerequisite requiring separately authorized off-host write-once storage and a distinct verification principal; neither was used or claimed here.
