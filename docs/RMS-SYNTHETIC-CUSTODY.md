# MAU-170 — synthetic result custody

Fixture-only implementation under the November 22, 2026 build direction and MAU-25 plan revision 3. This candidate combines the reviewed MAU-168 gate tree `512765d8163d2936fc9ec574e4a4428bd9ae0cf2` (PR #13) and the MAU-159 Runs/Results contract `017927f18b0b1150a23bb824e16947aac99beefd` (PR #6) on the MAU-170 branch only. Neither input branch, installed RMS, nor a reserved target is changed. This is not release or Stage 2 acceptance.

## Operator contract

From an authenticated **Runs and Results → exact result version**, an assigned fixture actor can open **Synthetic custody for this exact result version**. The page uses private, non-cacheable HTML and CSRF-protected form POSTs. A scoped reader sees only the recorded event IDs and states; a scoped operator has to pass the exact operation checks to append an event. Unscoped lookups are indistinguishable from missing custody objects. There is no bulk/search/export-index endpoint or new JSON write route. The separate download is an attachment, not network dispatch or a public artifact URL.

- `stage` → `verify` → `seal` reuses the existing bounded, locally sealed `RunResultVersion` original (1–8192 bytes). The original result's embedded seal is an integrity record, not permission to use or export. The new custody state and rights never rewrite it. Each append pins the database/object watermark, approved context, result predecessor and earlier receipt hash. Corrected results start a new stream; their first event links to the previous exact custody head. A corrected or stale plan/result cannot be used to register or download a new export of its previous version.
- Settings are absent by default. Only the local fixture definition enables custody under an exact stable `RMS_SYNTHETIC_STAGE_GATES` plan entry (`custody.enabled` plus operation bindings, see `tests.django_custody_tests.grants`). The MAU-168 validators check reference, revision, policy, operation, exact subject, status, interval and digest; rights additionally bind principal, purpose `synthetic_custody_only` and destination `fixture:local-download`. Check every recorded binding again before a new append or download. The settings are a synthetic input, not an RMS approval screen, live Paperclip observation, or activated grant.
- Optimistic sequence and actor-scoped idempotency use the shared transaction service. Same-key replay yields only the original event receipt, not export bytes or current permission. A stale sequence or different payload reuse is rejected without another event or idempotency record. Corrupt, missing, drifted or unauthorized input denies sealing and download; a scoped operator can record a terminal `reconcile` quarantine on a failing existing claim. No automatic deletion, repair, unquarantine, scanning, or hidden state changes. A truthful replacement needs a new result version.
- `export` is a single immutable receipt per result. Its initiator can retrieve canonical JSON with its exact manifest, right/authority receipt, stable IDs, artifact SHA-256 and base64 of the unchanged original. A second retrieval with valid current bindings is byte-identical. If the inputs or rights change, the download closes; previously downloaded copies are not recalled. No generic arbitrary-destination or real research export is included.
- The existing Run Result `/artifact` API retains its exact result artifact manifest and response format. On a plan with a custody setting or any historical custody receipt, it releases original bytes only if the caller could retrieve the custody export: the caller must be its initiator, the exact result and plan must still be current, and all bindings and bytes must verify. A missing/disabled custody configuration cannot reopen bytes for a plan with receipts. Plans with neither an opt-in nor receipts retain the existing RMS artifact contract. Result metadata reads and historical receipts are unchanged; they are not byte downloads.

## Migration and recovery

`0011_custody` joins the two published `0010` leaves without renumbering either. It creates one UUID-keyed table with append-only triggers, transition/lineage checking, and sequence uniqueness; no content rewrite, sidecar object storage, additional database sequence, or backfill. A down-migration refuses a populated custody table. Preserve the pre-change backup and migration receipt; if a candidate fails, keep writes gated. Use a new isolated target and the newest matching immutable checkpoint, and reconcile writes before any reopen. Never reverse populated custody or fall back to a stale source. The test fixture copies are read-only at the filesystem level and hashed; the owner can still replace either copy or receipt. That is not immutable independent retention.

The `scripts/rms-python/rehearse-custody.sh` probe is offline and restricted to a run-owned PostgreSQL 17.11 Unix socket (`fixture_admin`, non-superuser `fixture_owner`). It reuses the published Runs `pgcrypto` and ordinary-runtime grant checks; the new custody grant is only `SELECT, INSERT`, with no direct trigger execution, row mutation, or DDL. The gate-table read in the rehearsal is for its checkpoint, not a proposed production intake/gate ACL.

Each restore target is created with `ALLOW_CONNECTIONS false`. From the maintenance database, one transaction removes PUBLIC and ordinary database privileges, grants the temporary verifier `CONNECT`, and enables connections for controlled import and verification. Import uses the precreated target in a single transaction, without `pg_restore --create`. The verifier connects under its own login and assumes the runtime role for exact table ACL, enabled trigger, scope/revocation, export, watermark, and history checks. Only after the verifier's receipt matches the sealed checkpoint does a transaction remove the verifier's `CONNECT` and grant it to the ordinary runtime login. An unrelated login remains denied. A second disposable target is deliberately reconciled against the wrong checkpoint; the same gate rejects it without granting runtime access. Both ordinary logins are probed at creation, before import, after import, and on their respective release or rejection paths. These checks exercise database roles on a private fixture socket, not production authentication or independent custody.

The manifest contains stable result ID mapping, source/target watermarks, exact migration/tool/dump digests, the digest of `restore-access.log`, and down-migration refusal. The fixture probe records hashes, not a second application export route. Importing or deploying is not authorized by this document.

Reproduce with the locked `.venv` and a disposable PostgreSQL cluster (never an installed database):

```sh
.venv/bin/python manage.py check
.venv/bin/python manage.py makemigrations --check --dry-run
.venv/bin/python manage.py test tests.django_custody_tests tests.django_stage_gate_tests \
  tests.django_run_result_tests.RunResultTests tests.django_run_assurance_page_tests --noinput -v 1
bash scripts/rms-python/rehearse-custody.sh
```

The last command additionally needs `PAPERCLIP_RUN_SCRATCH_DIR`, `RMS_CUSTODY_PGBIN`, loader path for the pinned build, and `RMS_DB_HOST`/`RMS_DB_PORT` for a fresh private socket in that scratch root. It generates a fresh local recovery manifest and deletes only its generated fixture databases and roles on exit. `tests.django_custody_tests` uses the existing invented HN fixture plus a synthetic attempt/results path; it checks scope, CSRF, rights and stale conflicts, idempotency, concurrent writers, missing/corrupt bytes, lineage and history. Run only with invented fixtures. No new credentials, hosted access, budget, or spend were required. Actual independent custody would require separate authority for off-host write-once storage, restricted identities, a transparent retention policy and an independent verifier; neither a second local database nor checksums meet that requirement.
