# RMS-VS-1 backend development contract

This repository implements the approved local, synthetic-only Source persistence/API slice. It is not a deployed service, Stage 1 acceptance, independent Risk acceptance, or authority to use real research data.

## Pinned stack

- CPython 3.13.15
- Django 5.2.17 LTS
- Django REST Framework 3.18.1
- psycopg / psycopg-binary 3.3.6
- PostgreSQL 17.11

`requirements.lock` pins every Python artifact by SHA-256. `stack.lock` records the selected CPython, wheel, PostgreSQL, and runtime-library artifacts and hashes. The task-local binaries themselves are deliberately excluded from Git.

## Persistence and migration behavior

`rms.0001_initial` creates `Source`, immutable `SourceVersion`, immutable `SourceManifest`, and immutable `IdempotencyRecord`, including database-generated byte lengths and SHA-256 values. It enables PostgreSQL's bundled `pgcrypto` extension for digest expressions.

`rms.0002_source_invariants` adds the same-Source composite predecessor foreign key and database triggers that:

- reject direct Source mutation/deletion while allowing only nested one-step watermark advancement;
- serialize a version append on the Source row and require exactly the next version/immediate predecessor;
- reject SourceVersion, SourceManifest, and IdempotencyRecord updates/deletes; and
- reproduce the canonical manifest from ordered stored versions and reject any byte mismatch.

Apply only to an authorized empty/task-scoped PostgreSQL database:

```console
.paperclip-runtime/venv/bin/python manage.py migrate --noinput
```

A migration failure is transactional. Stop the application, preserve the database and command output, diagnose the failed migration, and retry only after review. Do not fake a migration, edit applied migration history, substitute SQLite, or delete evidence rows. Because this slice is not deployed, rollback is abandonment of the unmerged feature branch and task database while preserving commits/evidence. `0002` has explicit reverse SQL for a reviewed development rollback; `0001` follows Django's normal table-drop reverse and must never be reversed against evidence to obtain a passing result.

## API contract

HTTP Basic authentication is permitted only on a developer-run loopback/task-scoped instance. Credentials are created out of band and never committed. An authenticated user belongs to exactly the relevant Django group:

- `editor`: all five Source routes plus readiness;
- `founder_viewer`: GET routes and readiness only;
- anonymous: denied with `401` before object retrieval.

Routes:

```text
POST /api/v1/sources
POST /api/v1/sources/{source_id}/corrections
GET  /api/v1/sources/{source_id}
GET  /api/v1/sources/{source_id}/versions
GET  /api/v1/sources/{source_id}/manifest
GET  /api/v1/readiness
```

Both writes require `Idempotency-Key`. Correction also requires `expected_latest_version`. The service acquires a transaction-scoped advisory lock for a global idempotency key, then uses a Source row lock for corrections. The Source version, canonical manifest snapshot, exact response bytes, idempotency record, and watermark commit atomically. A stale/concurrent loser has no partial row.

## Deterministic fixture

`RMS-VS-1-F1` contains only invented bytes. Loading it twice verifies and retains the same fixed internal UUIDs, timestamps, ordered versions, and canonical manifests:

```console
.paperclip-runtime/venv/bin/python manage.py load_rms_vs_1_fixture
.paperclip-runtime/venv/bin/python manage.py export_rms_vs_1_fixture
```

The export contains public history metadata and Base64-encoded canonical manifest bytes; it never contains raw Source content. A mismatch stops with `CommandError` rather than replacing rows.

## Development verification

Set the `RMS_DB_*` variables to an authorized PostgreSQL 17.11 test database. Exact commands used by Backend development are:

```console
PYTHONDONTWRITEBYTECODE=1 .paperclip-runtime/venv/bin/python -m unittest discover -v
PYTHONDONTWRITEBYTECODE=1 .paperclip-runtime/venv/bin/python -m unittest tests.test_source_versions -v
PYTHONDONTWRITEBYTECODE=1 .paperclip-runtime/venv/bin/python manage.py test tests.django_source_api_tests tests.django_fixture_tests tests.django_contract_tests -v 2
.paperclip-runtime/venv/bin/python manage.py makemigrations --check --dry-run
.paperclip-runtime/venv/bin/python manage.py check
```

The Django development suite covers editor/viewer/anonymous permissions, exact validation failures, append-only database rejection, idempotent replay/conflict, stale correction rollback, one-winner concurrent correction, manifest/database equality, readiness, and deterministic fixture load/export. The unchanged public suite remains separately discoverable and passing. Test Engineering's exact-candidate verdict remains independent.

## Known limitations

- Local Basic authentication is not suitable for deployment and conveys no operational security claim.
- PostgreSQL migration/application tests require the pinned Debian 13 amd64 task-local runtime.
- There is no page, search, connector, deployment, background worker, shared service, real/protected data, or broader RMS workflow in this backend slice.
